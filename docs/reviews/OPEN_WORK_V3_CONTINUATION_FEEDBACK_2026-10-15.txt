## B. Findings

No confirmed production defects.

**F1: confirmed test-portability defect (P3).**
- **Where:** `tests/integration/test_save_slots.py:174`, in `test_link_count_metadata_rejects_alias`.
- **Trigger:** CPython 3.13.12 on Linux.
- **Expected vs actual:** The test double calls `os.stat_result(fields, {"st_file_attributes": …})`, which raises `TypeError: duplicate or unexpected field name(s)` on POSIX. The test fails before reaching production code. It passed on 3.12.3/Linux in run A, so the cause is the interaction of the Python version and the OS.
- **Production guard:** The guard it targets (`sqlite_store.py:51`, `st_nlink > 1`) is not exercised on this platform. The guard itself reads correctly.
- **Contract basis:** The README gate runs the whole suite, so the suite should pass on any supported host.
- **Repair:** Build the fake with `os.stat_result(fields)` and leave out the Windows-only extras. I applied this to a scratch copy and the test passes. The packet itself is unchanged.

**F2: maintainability (P3).** `client_worker.py` (about lines 77–82) classifies player-visible errors by exact message text (`"NO_RETRY"`, `"QUEST_UNAVAILABLE"`). A typed exception would be safer. It is correct today.

**F3: unverified design note (P3).**
- **What happens:** `GenerationBudget.reconcile` takes a non-blocking lock. If it fails after a successful provider response, `GeminiDialogue.generate` raises `GENERATION_BUDGET_UNAVAILABLE` and the response is lost.
- **Accounting is safe:** The 20,000-token reservation stays on the ledger, so spend is never under-counted. It only wastes a call, and the budget behavior is documented as intentional.
- **Not covered:** The CP05 disposition justifies the non-blocking lock only for failures *before* a reservation is published.
- **Status:** Static reading only; I did not reproduce it.
- **Possible repair:** A bounded retry on reconcile.

**F4: scalability hypothesis (P4).** `engine_bridge.response()` sends the whole narrative catalog on every update, while the frame limit is 1 MiB. `write_frame` raises `ValueError` outside the per-request try block, which would end the process. The catalog is about 1.6 KB today, so this is unreachable now.

**F5: unverified (P4).** The C# `BrainConnection` starts its 10-second response timer at construction, and that must cover the Python cold start, the durable open and the first attach. A slow start could time out and kill the child process. I ran no native timings. (The deadline covers whatever the Brain does, so any single slow step counts.)

**F6: intentional behavior, noted only (P4).**
- **What happens:** The approved-preset path in `PlayRoom.Start()` reads the pin from `harbor-memory-v1.sha256`, a file stored next to the content it pins.
- **Verified:** The pin matches `a8ec2de9…` (the SHA-256 of `harbor-memory-v1.json`), and the candidate bytes hash to the approval's `output_sha256` (`bcf4719f…`).
- **Status:** Your CP05 disposition already calls the preset a local development harness, not production authentication.

**Confirmed against the contracts:**
- **Memory:** Memory entries are strictly derived from the quest stage (`MemoryCheckpointPolicy`): 0 entries at stage 0, 1 at stages 1–2, 2 at stage 3. An unreported defeat (stage 2) therefore cannot appear as eyewitness knowledge.
- **Quest steps:** Quest steps are single-step with endpoint checks. The 0→2 net step is deliberate, for an enemy that is already dead when the quest is accepted.
- **Reward:** The reward fact is emitted only on 2→3, so it can fire only once.
- **Transport:** The Gemini transport uses a fixed HTTPS origin, no proxy and no redirects.
- **Key handling:** The key goes to the child process over stdin, never on argv or in the URL.
- **Child process:** The child is killed and reaped on any exception. Network responses are capped at 256 KiB.
- **API key source:** Only `GEMINI_API_KEY` is read, so there is no spare-key rotation.
- **Release hooks:** The dev verification hooks in the Unity scripts sit inside `#if UNITY_EDITOR || DEVELOPMENT_BUILD`. `PlaytestBuild.Build()` fails the build if `LiveVerification` is present in the release assembly.
