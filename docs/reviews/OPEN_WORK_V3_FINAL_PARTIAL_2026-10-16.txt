## Corrections to my previous report

**Saved-clone finding: not a defect, reclassified as intentional.** The 8-clone cap is specified in CORE-05 §7 and recorded as CP01-F3, and `test_missing_and_clone_limit` asserts it. My reproduction (8 sessions, then `SAVE_LIMIT`) shows the contract working as written.
- **Why automatic deletion is unsafe:** the contract keeps the active clone on close, and later `--working` resume uses that returned path, so a clone can hold real progress.
- **Ownership:** a file may be deleted only if this same live session created it. Ownership is never inferred from a filename, and startup must not delete unknown leftovers. Cleanup is explicitly "later work".
- **What remains is a product gap:** the player text is a generic "size or managed file count limit reached". A safe repair is an explicit, user-invoked clone listing with tick and revision that never touches the active path, plus an error message naming the directory and count.

**Other retractions:**
- The non-blocking budget lock and the coarse HTTP codes are intentional (CP05 integration P3).
- Export failure after the file replace is `SAVE_EXPORT_UNCERTAIN` by contract (CORE-05 §5).
- `inspect()` is fine as written, because `_read_file` already wraps everything into `SAVE_CORRUPT`.

## Findings

**R1: Low, confirmed (reproduced at `fetch` level).** `gemini_transport.fetch` catches `URLError`, `TimeoutError` and `OSError`, but not `http.client.HTTPException`.
- **Trigger:** a local server returning a malformed status line raised `BadStatusLine`, and a truncated chunked body raised `IncompleteRead`. Both escaped `fetch` and `main`.
- **Effect:** the child process dies, and the parent maps the non-zero exit to `GENERATION_OUTPUT`. A transient network fault is therefore never retried. The key does not leak, because stderr is discarded.
- **Repair:** catch `http.client.HTTPException` in `fetch` and raise `GENERATION_TRANSIENT`.
