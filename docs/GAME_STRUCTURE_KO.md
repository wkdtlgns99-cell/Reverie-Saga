## 1. 외부 제작 — 이미지·모델·소리·스토리 재료

AI와 제작 도구가 콘텐츠를 만들고, 검수한 결과를 게임에 넣는 영역이다.

| 분야 | 만드는 것 | 게임에서 사용하는 방식 |
|---|---|---|
| 2D 이미지 | NPC 초상화, 몬스터 일러스트, 아이템 아이콘, UI 이미지 | 해당 캐릭터·아이템·화면에 연결해 표시 |
| 3D 캐릭터 | 종족별 몸체, 얼굴·머리카락, 의상·갑옷·무기 | 부품을 조합해 NPC와 플레이어 외형 구성 |
| 3D 환경 | 건물, 가구, 길, 바위, 나무, 유적, 지역별 소품 | 준비된 부품을 조합해 마을·던전·지역 구성 |
| 애니메이션 | 걷기, 공격, 피격, 대기, 상호작용 동작 | 내부 시스템이 확정한 행동을 화면에서 재생 |
| 음악 | 지역·전투·사건·분위기별 BGM | 현재 장소와 상황에 맞춰 선택·전환 |
| 효과음·짧은 음성 | 무기, 발걸음, 환경음, 마법, 감탄·비명·짧은 말소리 | 행동·사건·캐릭터 성격에 맞춰 재생 |
| 세계관·스토리 소재 | 역사, 신화, 문화, 세력 갈등, 지역 전설, 사건·퀘스트 원형 | 세계 생성과 퀘스트 구성의 바탕으로 사용 |
| 캐릭터 설정 소재 | 외형, 배경, 성격, 말투, 목표, 인간관계 원형 | 내부 NPC 데이터로 변환해 사용 |

제작 흐름:

**사용자가 방향 지정 → AI가 후보 제작 → 기술·내용·스타일 검사 → 승인 → 게임에 연결 → 실제 화면에서 확인**

예를 들어 AI가 갑옷 모델을 만들어도 크기·관절·무기 위치가 맞고, 게임에서 정상 표시되는지 확인해야 제작이 끝난다.
이미지·모델·음악은 기본적으로 미리 만들어 둔 라이브러리를 사용한다. 플레이할 때마다 새 모델이나 음악을 생성하는 구조는 아니다.
현재 MASTER의 2D 제작 방향은 SD 1.5 + LoRA + ADetailer이며, 다른 제작 분야의 서비스와 도구는 별도 선택·검증 대상이다.
사용자는 방향·우선순위·검토·승인을 맡고, 대량의 코드·그림·모델·음악을 직접 제작하는 것이 기본 전제는 아니다.

## 2. 내부 계산 — 게임 세계를 운영하는 Python 시스템

실제로 무슨 일이 일어났는지 결정하는 게임 규칙이다.

| 시스템 | 계산·판단하는 내용 |
|---|---|
| 이동·공간 | 이동 가능 여부, 거리, 사거리, 경로, 장소 간 연결, 문·장애물 |
| 전투 | 행동 가능 여부, 공격·방어·피해, 체력·기력, 상태 효과, 전투 결과 |
| 물체·환경 | 재질과 물체의 상호작용, 파괴·붕괴, 시야·조명, 소음·은신, 온도·날씨·환경 위험 |
| 생존·신체 상태 | 부상, 질병·중독, 음식·부패, 수면·피로, 장비 무게와 부담 |
| 시간·예약 사건 | 행동에 따른 시간 경과, 낮·밤·달력, 나중에 발생할 사건 |
| 경제·세력·지역 변화 | 물자 공급, 무역, 가격, 치안, 세력 관계, 지역 사건의 파급 |
| NPC 행동·인지 | 성격·감정·관계·목표·기억을 바탕으로 행동 선택, 소문 전달, 화면 밖 활동 |
| 퀘스트·이벤트 | 시작 조건, 진행 단계, 목표 달성, 실패, 보고, 보상, 후속 변화 |
| 저장·복구와의 연결 | 확정된 상태를 6번에 전달하고, 불러온 상태로 시뮬레이션을 재개 |

전투에서는 공격 능력·방어 상태·거리·장비·상태 효과를 입력으로 받아 결과를 계산하는 코드가 필요하다.
구체적인 공식과 수치는 각 시스템을 설계하면서 정한다. 이 설명 자체가 새 계산식을 확정하지 않는다.

제작 단계에서 AI가 계산식 설계와 코드 작성을 도울 수 있다. 채택한 규칙은 게임 코드가 실행한다.
플레이 중 LLM이 매번 다른 피해 공식을 만들어 적용하는 방식은 아니다.
NPC의 자율 행동도 내부 시스템의 역할이다. 예를 들어 욕심이 많고 플레이어를 불신하며 식량이 부족한 상인의
성격·상황·목표 데이터를 보고 거래·경계·이동 같은 행동을 선택하도록 만든다.
계산은 Python 실행기가 수행한다. VS Code는 개발용 편집기이다.

## 3. 내부 데이터 — NPC·아이템·퀘스트를 담는 템플릿

계산 코드가 공통 규칙이라면, 데이터 템플릿은 각 대상의 성질과 조건을 담는 정해진 양식이다.
아래 필드 목록은 이해를 위한 예시이며, 최종 형식이 모두 확정됐다는 뜻은 아니다.

| 템플릿 | 담는 정보의 예 |
|---|---|
| NPC | 이름, 외형, 성격, 소속, 능력, 목표, 말투, 관계, 기억 |
| 몬스터 | 종류, 능력, 행동 성향, 서식 조건, 공격 방식, 외형 |
| 아이템·장비 | 종류, 재질, 무게, 성능, 사용 조건, 외형·아이콘 연결 |
| 기술·상태 효과 | 대상, 범위, 비용, 지속 조건, 적용할 효과 |
| 물체·재질 | 물체 종류, 재질 특성, 파괴·상호작용에 필요한 값 |
| 지역·시설 | 위치, 연결 관계, 기후, 자원, 주민·세력, 배치 조건 |
| 세력 | 성향, 목표, 관계, 자원, 영향 범위 |
| 퀘스트 | 의뢰자, 시작 조건, 목표, 단계, 실패 조건, 보상, 후속 영향 |
| 이벤트 | 발생 조건, 대상, 시점, 적용할 변화, 후속 사건 |
| 대사 | 화자, 상황·성격·관계 조건, 사용할 문장 |

**AI가 내용 후보를 만든다 → 정해진 데이터 양식으로 변환한다 → 검사·채택한다 → 내부 코드가 읽고 실행한다.**

“포구 경비병의 의뢰”라는 이야기만 있어서는 퀘스트가 실행되지 않는다. 실제 의뢰자, 대상 적, 완료 조건,
보고 단계, 보상이 내부 데이터로 연결돼야 한다.
AI가 “시간을 되감는 마법”이라는 문장을 만들었다고 그 기능이 자동으로 생기지 않는다.
내부 엔진이 지원하는 효과를 조합하거나, 해당 기능을 별도로 구현해야 한다.

## 4. 플레이 중 AI — 세계·기억을 참고해 콘텐츠 생성

게임에 들어가는 LLM의 역할이다. 현재 최종 설계는 새 게임, 세계 생성, 장 전환, 로딩·준비 같은 생성 구간을 중심으로 사용한다.

| AI에 주는 자료 | 용도 |
|---|---|
| 세계관·지역·세력 설정 | 게임 분위기와 설정 유지 |
| 확정된 사건·세계 상태 | 이미 벌어진 사실과 모순 방지 |
| NPC 성격·목표·말투 | 캐릭터다운 표현과 콘텐츠 구성 |
| 플레이어와의 관계·기억 | 이전 행동을 반영한 반응 |
| 사용할 수 있는 퀘스트·효과 양식 | 실행 가능한 콘텐츠 생성 |
| 관련 기록의 검색 결과 | 긴 기록에서 이번 생성에 필요한 맥락 제공 |

기억 검색 시스템은 키워드 검색, 임베딩·벡터 검색, 요약 등을 이용해 필요한 기록을 찾는 구조이다.
구체적인 검색 기술은 아직 선택·구현되지 않았다.

- 실제 기억: “플레이어가 이 NPC를 구했다”라는 확정 기록.
- 검색용 자료: 그 기록을 찾기 위한 벡터·색인·요약.

AI가 만들 수 있는 결과는 NPC 배경·대사, 지역 설명, 사건·퀘스트 후보 등이다.
결과를 검사하고 채택한 뒤 저장하면, 내부 게임 시스템이 일반 데이터처럼 사용한다.
퀘스트 달성·피해·보상·실제 관계 변화는 내부 코드가 결정한다. AI는 사실에 맞는 콘텐츠와 새로운 후보를 만든다.
매 이동·공격마다 LLM을 호출하는 것이 필수는 아니다. NPC와 대화할 때마다 실시간 자유 대화를 생성하는 기능은
현재 설계의 필수 기능으로 확정된 것이 아니다. 이를 원하면 별도 요구사항으로 명확히 정해야 한다.
최종 설계의 선택적 런타임 API 사용은 플레이어가 지원되는 키를 제공하는 방향이며, 구체적인 서비스·요금·한도는 따로 확인한다.

## 5. 화면·연출 — 그래픽 엔진이 담당하는 부분

현재는 Unity를 연결했으며 최종 엔진 선택은 별도 검증 대상이다.

| 영역 | 담당 내용 |
|---|---|
| 입력 | 키보드·패드·버튼 입력을 게임 명령으로 전달 |
| 배경·캐릭터 표시 | 준비된 3D 부품과 외형 데이터를 조합해 렌더링 |
| HD-2D 표현 | 저해상도 렌더링, 픽셀 확대, 툰 표현, 조명·깊이·윤곽 |
| 카메라 | 필요한 회전·시점·장면 구성 |
| 행동 연출 | 공격·피격·이동 애니메이션과 이펙트 |
| UI·대화 | 상태, 아이템, 퀘스트, 초상화, 대사 표시 |
| 오디오 | 상황별 음악·효과음·짧은 음성 재생 |

Python이 적에게 피해가 적용됐음을 확정하면, 그래픽 엔진이 타격 동작·피격 효과·체력 표시·소리를 재생한다.
시야·소음이 실제 게임 판정에 미치는 영향은 2번, 그것을 빛과 소리로 표현하는 것은 5번이다.

## 6. 저장 — 세계·콘텐츠·제작 파일을 구분해 보관

| 저장 대상 | 보관하는 것 |
|---|---|
| 게임 진행 상태 | 위치, 체력, 시간, 퀘스트 진행, 관계, 기억, 세계 변화, 예약 사건 |
| 채택한 생성 콘텐츠 | 해당 플레이에 사용한 세계·NPC·퀘스트·대사 데이터 |
| 제작 에셋 | 이미지, 3D 모델, 애니메이션, 음악·효과음 파일 |
| 검색용 자료 | 기억 색인, 벡터, 요약 등 |
| 제작·검수 기록 | 생성 출처, 버전, 승인·검사 결과, 연결 대상 |

채택한 생성 콘텐츠를 저장하는 이유는 불러오기나 재현 때 AI가 내용을 새로 만들어 과거 사실을 바꾸지 않게 하기 위해서이다.
큰 이미지·모델·음악 파일은 일반 저장 파일마다 복사하지 않고 게임 에셋으로 관리한다.
검색용 자료는 확정된 기억·사건 기록과 구분한다. 검색 자료를 다시 만들더라도 원래 사실은 유지되어야 한다.
저장 실패·중단 후 복구·중복 명령 방지 역시 이 영역과 내부 계산의 연결에 해당한다.
최종 플레이어는 실행 파일로 게임을 이용하며, Python 개발 환경이나 DB 서버를 직접 준비할 필요가 없도록 배포하는 것이 목표이다.

## 7. 실제로 모두 연결되는 예

“도적 때문에 무역이 끊긴 포구”를 예로 들면 다음과 같다. 아래 과정은 최종 연결 사례이며 모두 구현됐다는 뜻은 아니다.

1. 외부 제작(1번): 포구 건물·경비병·도적 모델, 초상화, 음악, 지역 설정을 준비한다.
2. 내부 템플릿(3번): 포구·경비병·도적·도로·무역·퀘스트 데이터를 구성한다.
3. 내부 계산(2번): 도적 활동으로 무역과 물자 공급이 줄고, 가격·치안이 변한다.
4. AI 콘텐츠(4번): 관련 설정과 기록을 참고해 의뢰 내용·대사·후속 사건 후보를 만든다. 검사·채택 후 사용한다.
5. 플레이(2번): 플레이어가 도적을 처치하면 내부 코드가 결과와 퀘스트 진행을 확정한다.
6. 세계 변화(2번·6번): 보상·관계·기억·무역 상태에 정해진 변화가 적용되고 기록된다.
7. 화면·소리(5번): 캐릭터 행동, 대사, 상태 표시, 음악으로 결과를 보여준다.
8. 저장(6번): 그 플레이에서 일어난 사실과 채택된 콘텐츠가 유지된다.

7번은 독립적인 게임 엔진 모듈이 아니라, 여러 영역을 실제 플레이 흐름으로 연결하는 설명·통합 검증이다.

## 앞으로 작업 설명을 받을 때

“지금 이게 어디에 해당하는 거야?”라고 물으면, 영어 대응 문서를 읽고 주된 번호와 이름을 알려준다.
여러 영역에 걸치면 관련 번호도 함께 표시하고, 실제 구현·검증 완료와 설계·예정 상태를 구분한다.

예: “주로 4번 플레이 중 AI입니다. AI가 대사 후보를 만들며, 3번 양식으로 검사하고 6번에 저장합니다.”
문서·개발 도구·규칙 정리 같은 보조 작업은 지원하는 번호를 알려주되, 새 게임 기능을 구현했다고 표현하지 않는다.

## 기록 시점의 구현 상태

2026-10-14 기준 작은 내부 계산·저장 시스템, Unity 테스트 화면, 첫 퀘스트, 실제 Gemini 대사 생성 연결까지 검증했다.
광범위한 세계·NPC·장기 기억·검색·에셋 제작 체계는 이후 구현 목표이다.
이 문서의 시점 기록을 미래의 현재 상태로 사용하지 말고, 설명할 때 백로그와 실제 코드를 확인한다.
